# tele 通道排障手册

本文沉淀 2026-10-10 全链路体检中查出的全部问题与修法。遇到「tele 不秒回」先看这里，  
再跑 `bridge_ctl.py status`。

---

## 一、故障分类：先判断是哪一段

| 现象                     | 断在哪一段                       | 怎么看                    |
| ---------------------- | --------------------------- | ---------------------- |
| 手机发出去，桥接日志里**有**「收到 …」 | 收的方向是通的，断在我处理或回程            | `bridge_ctl.py logs`   |
| 手机发出去，日志里**没有**「收到」    | 桥接进程没跑 / 网关不通 / 密钥过期 / 端口漂移 | `bridge_ctl.py status` |
| 日志里「投递受阻」，然后是「已排队待补发」  | 网关或密钥问题                     | 同上                     |
| 日志里「补发成功」              | 自愈成功，无需人工干预                 | —                      |

---

## 二、五个已确认的坑（含原理）

### 1. 网关端口漂移 —— 今天失联三次的元凶

**现象**：桥接日志出现连续 `fetch failed`，几分钟后才自己恢复。

**原因**：WorkBuddy 的本机网关端口是**随机分配**的。不只在应用重启时变，**每开一个新窗口/  
新工作区就会换一个**。今天一天换过 6 个：  
`52116 → 49853 → 50294 → 51834 → 55013 → 55639`。

**官方文档、`~/.workbuddy/settings.json`、`app-config.json`、程序本体（app.asar）里  
都没有「固定端口」这个设置项** —— 查证过，改不了。

**已修**：bridge.js 现在

- 每 **5 秒**自检一次网关（原来是「投递失败才发现」，约 3 分钟）；
- **每次投递前**再确认一次端口；
- 探测失败时扫描 `127.0.0.1` 全部 LISTEN 端口，用密钥逐个打 `/api/v1/health` 找出真网关。

**结论**：端口随它飘，使用者无感，等同于固定。

> 曾评估「在固定端口上跑本地转发器」的方案 —— 效果完全一样，但在这台 4GB 的 Mac mini 上  
> 多一个常驻进程就多一个故障点，**不采用**。

### 2. 通道密钥 1 小时盲区 —— 唯一没根治的

**原因**：WorkBuddy 每次启动重新生成 `CODEBUDDY_GATEWAY_PASSWORD`，它**只存在于进程环境变量  
里、不落盘**。桥接由 `launchd` 启动，读的是 `secret` 文件。

**实测结论**：**macOS 不允许一个进程读取另一个进程的环境变量**（`ps eww -p <Electron pid>`  
拿不到 `env`），所以桥接**无法自行取回**新密钥。可行路径只有两条：

1. 在 WorkBuddy 会话内跑 `bridge_ctl.py refresh`（直接读环境变量，1 秒完成）；
2. 等每小时守护自动化任务刷新。

**兜底设计**：密钥过期期间消息**不会丢** —— `deliver()` 抛 `BAD_SECRET` 被判定为瞬时错误，  
进 `pending.json` 队列，退避重试，刷新成功后自动补发。

**给 Jack 的口径**：重启 WorkBuddy 后如果在 tele 发消息没反应，在 WorkBuddy 里说一句  
「刷密钥」即可。

### 3. RATE_LIMITED 排队 —— 「不秒回」的真正根因

**原因**：WorkBuddy 同一时间只跑一个任务。**Jack 在电脑上用 WorkBuddy 对话时，Agent 被占住，  
tele 的投递会被网关返回 429**，只能排队。

**已修**：

- 待补发上限从「3 小时 / 120 次」提到 **12 小时 / 600 次**；
- 遇 `RATE_LIMITED` 改为**退避 60 秒**再试（原来 10 秒重试，20 分钟就放弃并**丢弃消息**——  
  那条 20:58 的「什麼意思」就是这样被丢的，已向 Jack 说明）。

**这条改不了**：是单 Agent 的硬限制。正确用法是「急事走 WorkBuddy 对话，tele 适合人不在电脑前」。

### 4. Mac 会睡觉 —— 最严重但最容易被误判为「网络问题」

**现象**：整条通道全断，Jack 会以为是网络。

**原因**：这台机设的是「空闲就睡」，此前只靠 WorkBuddy 开着硬撑。**WorkBuddy 一关，Mac 就睡，  
tele 立即全断。**

**已修**：新增常驻 `launchd` 服务 `cn.yaowork.keepawake`（`caffeinate -i -s`），  
`KeepAlive=true`，24 小时不睡。`bridge_ctl.py install` 会一并安装。

### 5. 长任务被截断

**原因**：`config.json` 的 `reply_timeout_ms` 原来是 600000（10 分钟），复杂任务跑不完就断线。

**已修**：改成 **1800000（30 分钟）**。

## 三、什么情况不用管

- 日志里偶发 `轮询异常: timeout`/`aborted` —— 长轮询正常超时，代码里对瞬时错误做了每分钟  
  最多记一条的降噪。
- 日志出现 `getUpdates 失败(409)` —— 上一轮长轮询尚未释放，判为瞬时错误自动重试。
- 每天日志文件超 2MB 会自动截断重写，属正常。

## 四、维护动作清单

| 时机              | 动作                                |
| --------------- | --------------------------------- |
| WorkBuddy 重启后   | `bridge_ctl.py refresh`           |
| Jack 说「tele 没回」 | `bridge_ctl.py status` → 按结论处理    |
| 每隔一段时间          | `bridge_ctl.py status` 看有没有「需要处理」 |
| 换了工作区/目录        | `bridge_ctl.py install` 重装自启      |
| 完全不想要了          | `bridge_ctl.py uninstall`         |

## 五、关键文件位置

桥接目录（本机默认示例：`~/WorkBuddy/<时间戳>/telegram-bridge/`，脚本会自动定位，不写死路径）：

| 文件                               | 作用                                             | 可否手改                   |
| -------------------------------- | ---------------------------------------------- | ---------------------- |
| `config.json`                    | bot_token、allow_chats、gateway、reply_timeout_ms | 可改，改完 restart          |
| `secret`                         | 网关密钥（600 权限）                                   | 只由 refresh 写           |
| `gwport`                         | 上次定位到的网关端口提示                                   | 只由脚本/bridge 写          |
| `state.json`                     | 长轮询游标                                          | **不要动**，会漏收或重复         |
| `pending.json`                   | 待补发队列                                          | 只读，必要时 `pending clear` |
| `bridge.log` / `launchd.err.log` | 日志                                             | 只读                     |

launchd 服务：`~/Library/LaunchAgents/cn.yaowork.telegram-bridge.plist`、  
`~/Library/LaunchAgents/cn.yaowork.keepawake.plist`

定时守护自动化：**「Telegram 桥接守护（刷新密钥 + 保活）」**，每小时的第 0/5/10/…/55 分钟  
各跑一次。
